# eIDAS 合格状态：在盖戳当时记录，而不是验证时再查

非合格时间戳和合格时间戳之间隔着的不是技术，是举证责任。

- **eIDAS 第 41(1) 条** —— 非合格时间戳不得仅因其为电子形式或非合格而被否定证据资格。它可以举证。
- **eIDAS 第 41(2) 条** —— 只有合格时间戳享有时间准确性与数据完整性的**法律推定**。举证责任因此倒置给质疑方。

用非合格 TSA，举证责任在你这边；用合格 TSA，在对方那边。这就是全部差别，也是本功能存在的唯一理由。

## 为什么必须在盖戳当时记

合格资质会变。它会被暂停、被撤销；TSP 每轮换一次签名密钥，可信列表里就多出一条状态时间线彼此独立的新条目。

所以「这份时间戳是不是合格的」这个问题，**在不同时刻问会得到不同答案**，而只有一个答案是对的：盖戳那一刻的答案。等到三年后出纠纷再去查可信列表，查到的是三年后的状态，回答的是另一个问题。

这正是本库整个存在的理由——记录证据在决策时刻的状态，而不是记录"查过"——原封不动地出现在它自己的信任根上。

## 怎么用

合格性判定需要一份可信列表快照。快照离线构建，查询时零依赖。

```console
$ pip install tg-attest[eutl]
$ python -m tg_attest.eutl_build -o eutl_snapshot.json
```

构建过程：下载 LOTL → 用官方公报公布的证书验签 → 逐个下载成员国列表 → 用 LOTL 里为该国登记的证书验签 → 抽取全部 `TSA/QTST` 条目及其完整状态历史 → 写出一份纯 JSON。约 26 MB 下载量，两分钟上下，产出约 2 MB。

写入路径只读这份 JSON：

```python
from tg_attest import AnchorQueue, Snapshot

q = AnchorQueue(("http://your-qtsp/tsa",), eutl=Snapshot.load("eutl_snapshot.json"))
q.enqueue(epoch.epoch_id, epoch.epoch_hash())
a = q.flush()

a.tsa_qualified        # True / False / None
a.eutl_ref             # "BE:81:0001" —— 国别:列表序号:条目序号
a.qualified_checked_at
a.qualified_reason     # 为什么是这个结论
```

**判定本身不发网络请求。** 它是一次索引查找加一次时间区间比较，跑在生产决策热路径上没有问题。把"取回并验证可信列表"和"查一下这把公钥当时合不合格"当成同一件事，是这个功能最容易犯的架构错误。

导出披露包时把 anchor 一并传进去，声明才会写进包里：

```python
export_bundle(ledger, seq, "d.json", anchor=a)
```

审计方复核，用他自己构建的快照，不是你给的：

```console
$ python -m tg_attest.cli d.json --ca ca.pem --eutl his_own_snapshot.json
```

## 三值语义，不要用真值判断

| 值 | 含义 |
|---|---|
| `True` | 查过了，盖戳当时该服务在可信列表上且状态为 `granted` |
| `False` | 查过了，不合格：不在列表上／状态非 `granted`／早于 eIDAS 适用日 |
| `None` | **没查**：没给快照、没装依赖、或该国列表在构建时取不到 |

`None` 和 `False` 的区别是这套设计的重点。把"查不到"记成"不合格"，等于把一次网络故障固化成一个法律结论，而这个结论会被写进不可变的记录里。反过来把"确实不在列表上"记成"没查"，等于放弃一个本可以确定的事实。

爱尔兰在 2026-08-16 的真实构建中就连不上（TLS 链不完整）。这不是假设。

## 判定流程

实现的是 ETSI TS 119 615 V1.3.1 第 4.6/4.7 节，每一步都能追到条款：

| 步骤 | 条款 | 做什么 |
|---|---|---|
| 1 | PRO-4.6.4-01 | 判定时刻早于 `2016-06-30T22:00:00Z` → 直接不合格 |
| 2 | PRO-4.6.4-02 | 由证书 subject 的 `C=` 选定成员国列表（`GB→UK`，`GR→EL`） |
| 3 | 5.5.1.1(d) | 只匹配 `…/Svctype/TSA/QTST`，其余 TSA 类型一概排除 |
| 4 | 5.5.3 | 路径长度 0：同一把公钥且同一个 subject 名字 |
| 5 | NOTE 1 | 路径长度 1：列表里登记的是签发 CA，token 证书由它签出 |
| 6 | PRO-4.3.4-03(b) | 取「生效时刻 ≤ 判定时刻」中最晚的一条状态 |
| 7 | PRO-4.6.4-08 | 证书 `O=` 必须匹配 TSP 名称（任一语言变体），否则不确定 |
| 8 | PRO-4.6.4-09 | 状态为 `granted` → 合格 |

第 1 步不是保守取舍：欧盟指令 1999/93/EC 下只有合格*证书*，没有合格时间戳这个概念。TS 119 612 附录 J(c) 规定，2016-07-01 当天所有 `QTST` 条目一律改写为 `withdrawn`，要拿到 `granted` 必须重新过合格性评定。（`CA/QC` 条目的迁移规则相反，迁移为 `granted`——最容易记混的一条。）

第 5 步不是细节。意大利可信列表里 29 条 `granted` 的 QTST 条目登记的**全部**是 CA 证书，没有一条是末端时间戳证书。只做直接匹配的实现，对意大利 100% 漏判。

## 信任根

两级，任何一级不验都等于没验。

1. **LOTL** 的签名证书必须在 **OJ C/2026/1944**（2026-04-15，明文取代 OJ C 276, 16.8.2019）公布的 6 张证书之内。本库只钉死这 6 个 SHA-256 摘要，证书本身从 LOTL 自带的自指指针里取，取到后逐一比对摘要。
2. **各成员国列表**的签名证书必须在 LOTL 里为该国登记的证书之内。

钉摘要而不是钉证书，是为了让信任根小到可以用眼睛核对——6 行十六进制，任何人打开公报就能自己查一遍。

签名格式是 enveloped XAdES。签名运算交给 `cryptography`（含 RSASSA-PSS，德国用的就是它），排除式 c14n 交给 `lxml`，本库只负责把 CID (EU) 2025/2164 附件第 3 点要求的引用/变换形状卡死：`URI=""` 的 Reference 恰好一个 Transforms、恰好两个 Transform、顺序为 enveloped-signature 然后 exc-c14n。**这条形状要求不是形式主义**——放任任意变换链，攻击者可以构造一个"只签了文档某个子集"的签名，摘要照样对得上，而被排除的那部分可以随便改。

## 把判定绑进哈希链

判定写在**下一个** epoch 的被哈希体里，因此受下一次锚定的时间戳保护。

```python
led.seal_epoch()                  # epoch N
a = queue.flush()                 # 锚定 N，判定在这一步做出
led.attach_anchor(a)              # 写回 token + 把判定排队
led.unbound_anchor_count()        # 1：判定已做出，尚未被哈希覆盖

led.append(...); led.seal_epoch() # epoch N+1，判定写进它的被哈希体
led.unbound_anchor_count()        # 0
queue.flush()                     # 锚定 N+1 —— 判定至此被时间戳覆盖
```

`AnchorAttestation` 里除了判定本身，还钉着 `anchored_hash`（被盖戳的那个
`epoch_hash`）、`token_sha256`（被判定的那个 token）和 `eutl_snapshot_sha256`
（判定依据的那份快照）。只写 `epoch_id` 是不够的：判定说的是「那个 token 的签发者
当时合格」，不指明是哪个 token，换一个再声明一次同样说得通。`Ledger.verify()`
会把这几项对回链上，对不上就报错——否则被哈希保护的只是「一段不会被改的自由
文本」，保证了它没被改，没保证它说的是这条链上的事。

导出时带上绑定 epoch，审计方才能自己验：

```python
export_bundle(led, seq, "d.json", anchor=a, include_binding=True)
```

默认不带。多一个 token 就多几 KB，而大多数披露只关心「这条记录当时存在」。
判定还没被任何 epoch 覆盖时传 `include_binding=True` 会直接报错，不会悄悄
导出一个让人以为受保护而其实没有的包。

`verify_bundle` 会校验绑定，但结果放在 `attestations` 里，**不进** `BUNDLE_REQUIRED_CHECKS`：
是否合格是法律分类，不该决定一个披露包在技术上是否有效。用非合格 TSA 的包完全
有效，只是举证责任在出具方那边。

**向后兼容**：判定为 `None` 时整个键不出现在被哈希的字典里，所以 0.1.0 时代那些
不含此键的披露包哈希值完全不变，继续验得过。反过来，判定**存在**却被删掉是查得
出来的——盖戳时的哈希含它，删掉后重算的不含它，两者不等。

## 这个功能防不住什么

写在前面：以下每一条都是真的缺口，不是免责声明。

**合格状态默认不受保护，除非你把它绑进链里。** 判定不能写进被判定的那个 `epoch_hash`——合格状态要拿到 token（TSA 签名证书在里面）之后才算得出来，而 `epoch_hash` 是**被盖戳的输入**，盖完再回写会让刚取回的时间戳当场失效。这与 `tsa_token` 必须排除是同一条约束，本项目在那上面已经踩过一次。

办法是往后挪一格：`Ledger.attach_anchor()` 把判定排队，下一次 `seal_epoch()` 把它写进**下一个** epoch 的被哈希体，于是它随下一次锚定的时间戳一起被覆盖。做法见上面的[把判定绑进哈希链](#把判定绑进哈希链)。

**但最后一次锚定的判定永远悬空。** 这是结构的固有性质，和「最后一批记录还没被封存」是同一回事。`Ledger.unbound_anchor_count()` 会把它报出来，要它归零就再封一个 epoch 并锚定。

**可信列表没有官方历史归档。** 只有 LOTL 有 pivot 存档，成员国列表没有。今天下载的列表回答的是今天的问题。所以审计方用今天的快照复算出的结果与包内声明不一致时，可能是资质在这段时间里变了，也可能是声明不实，**工具区分不了**。要可复现，就在盖戳时把那份签名过的列表 XML 连同判定结果一起归档——快照里记了每份列表的 SHA-256 与序列号，正是为了让这件事可对账。

**规范要求的双重判定本实现只做一次。** TS 119 615 PRO-4.7.4-06 要求在 `genTime` 与验证参考时刻各判一次、不一致即 `PROCESS_FAILED`。写入时这两个时刻相差毫秒，必然一致。差异会在以后出现，而那正是本字段存在的理由：以后再判，判的是那时的列表。这是对规范的有意偏离，写在这里而不是藏在实现里。

**证书没有 `C=` 时会降级为全表扫描**，并在 `qualified_reason` 里标注。严格照 PRO-4.6.4-02 执行会把一个命名不规范的证书判成"不合格"。这同样是有意偏离。

**路径长度 ≥2 不尝试。** 落到"未匹配"，也就是不合格。宁可少判合格，不要多判。

**吊销状态不查。** 本功能回答的是"这个服务当时在不在可信列表上"，不是"这张证书当时有没有被吊销"。后者是 `verify_token` 的证书链校验负责的范围，而那一层目前也不查 CRL/OCSP——见 [threat-model.md](threat-model.md)。

## 一个真实的坑：QTSP ≠ 合格时间戳

Actalis 是意大利的 QTSP。它的公开免费端点 `timestamp.actalis.it` 用的却是 `Actalis Time Stamping CA G1`——一个**没有**登记在可信列表上的非合格 CA。可信列表里 Actalis 的合格条目是另外两个 CA（`Actalis TSA 1 EIDAS` 和 `Actalis EU Qualified TimeStamp CA G1`），走的是付费服务。

本库对它的判定是 `False`，而这个判定是对的。

实测过的公开免费端点——FreeTSA、DigiCert、Sectigo、GlobalSign、Certum、SSL.com、Entrust、Apple、Actalis——**没有一个是合格的**。合格时间戳是付费服务，没有免费的。选 QTSP 时不要看"这家公司是不是 QTSP"，要看**你打算调的那个端点签出来的证书，在不在可信列表上**。这正是本功能替你回答的问题。
